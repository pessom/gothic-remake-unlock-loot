# Журнал решений

Почему проект устроен именно так. По каждому решению: что было не так, какие были варианты, что выбрали и что теперь нельзя ломать. Номера PR — в репозитории [pessom/gothic-remake-unlock-loot](https://github.com/pessom/gothic-remake-unlock-loot/pulls?q=is%3Apr).

Октябрь 2026.

---

## 1. Мастер связей не верит подсказкам на слово — PR #1

**Проблема.** Пользователи получали неверные связи и неверные шаги решения. Ядро решателя оказалось правильным: на тысячах случайных замков число ходов совпадает с независимым эталоном. Ошибки шли из мастера связей и подсказок.

Симуляция на 2000 случайных замков (сколько найденных решений не срабатывает в игре):

| Сценарий | До | После |
|---|---|---|
| Подсказка, в которой ошибочна одна связь | 1048 из 1284 | 0 |
| Подсказка на половину строк, одна связь ошибочна | 926 из 1170 | 0 |
| Пользователь не отметил плитку с уже известной связью | 1081 из 1721 | 0 |
| Честный ввод, пустая матрица | 0 | 0 |

**Причины и решения.**

1. **Подставленные связи считались проверенными.** Мастер больше не пробовал такие плитки, и ошибочная подсказка уходила прямо в решение. Ошибиться подсказка может легко: другой замок с теми же штифтами или прокачанный навык взлома (по словам самого сайта, тогда связи другие).
   *Решение:* подсказка — только ожидание. Подставленные ячейки помечаются как непроверенные (`WIZ_MEM.unv`, `wiz.unverified`), и каждую такую строку мастер сверяет одной пробой. Ожидаемые плитки отмечены на экране заранее. Цена — примерно один лишний ход на плитку.

2. **Успешная проба молча стирала известные связи.** Если пользователь не отметил плитку, связь которой уже была известна, мастер записывал «связи нет». Его позиции расходились с игрой, и все следующие команды и стартовые позиции решения становились неверными.
   *Решение:* известные связи отмечены заранее. Если отметку сняли (или нажали «Никто не дёрнулся»), мастер переспрашивает (`wizDroppedKnown`) и записывает «нет» только после второго нажатия.

3. **Подсказка искалась по штифтам, уже сдвинутым пробами.** Реальный пример из каталога: у левого сундука наверху в шахте Альберто штифты `1211`, после одной пробы — `1311`, а это сундук в тронном зале Гомеза с совсем другими связями.
   *Решение:* подсказку ищем только по исходным штифтам (`lockBasePins()`).

4. **Копилка пополнялась непроверенными конфигурациями** — при каждом нажатии «Взломать», ещё до того как замок открылся в игре.
   *Решение:* отправка в копилку только после «Сайт помог? → Да».

**Не ломать.** Строки из подсказки обязаны проходить пробу. Подсказка ищется по `lockBasePins()`, а не по текущим `pins`. Сценарии закреплены в `tests/wiz-test.mjs`: «wrong suggestion», «dropped known link».

## 2. Решатель всегда даёт минимум действий — PR #1

**Проблема.** Если коридор кратчайших путей был больше 200 000 состояний (плотные 7–8-плиточные замки), решатель переключался на жадный проход. Ходы оставались правильными, но действий в игре выходило до двух раз больше: на одном 8-плиточном замке 51 вместо 25. Тесты этого не ловили: фузз генерировал только 3–5 плиток.

**Варианты.** Поднять порог: точный DP на `Map` занимал ~440 МБ и ~4 с, что опасно на телефоне. Либо переписать DP.

**Решение.** Точный DP на типизированных массивах: коридор нумеруется по слоям, `best` — `Uint16Array`, `from` — один байт (номер хода и прошлая плитка). Жадная ветка удалена. На том же замке 25 действий и ~100 МБ.

**Не ломать.** В `tests/sol-test.mjs` есть фузз на 6 плиток и широкий 8-плиточный коридор (95 ходов, 24 переключения).

## 3. Каталог замков — один файл `locks.yaml` — PR #2, #6

**Проблема.** Список замков жил в четырёх ручных копиях — подсказка в решателе RU/EN и карточки каталога RU/EN — плюс `LOCK_PAGES`, разметка для поисковиков, статичные карточки и 39 страниц, собранных разовыми скриптами `tools/add-*.mjs`. Копии разошлись: одного замка не было в подсказках, разметка вела не туда, статичных карточек было 22 из 45.

**Что выбрали и почему.**
- **YAML** — так захотел владелец: файл удобно править руками. Браузер YAML не читает, поэтому генератор `tools/build-locks.mjs` собирает из него `site/locks/locks-data.js`, каталог (из шаблонов `tools/templates/`), страницы замков, редиректы и `sitemap.xml`.
- **Сборка только в CI.** Собранные файлы не хранятся в git, чтобы не было копий, которые снова разойдутся. Цена: локально нужен `npm run build:locks` (или `npm run serve`), а зеркало `raw.githack.com`, которое отдаёт файлы прямо из git, работает без подсказок по известным замкам.
- **Подсказки только из `locks.yaml`.** Крауд-подсказка `/suggest` из копилки сайтом больше не вызывается. Счётчик, аналитика, отзывы, копилка и «Живой топ» остались на воркере.
- **Штифты и связи записаны явно** (PR #6): `pins: [6, 3, 2, 1, 7]` и `links: {4: +2 -3 -5}`. Поле `code` убрано, код для ссылок генератор считает сам. Раньше, чтобы поправить одну связь, нужно было открыть сайт и переписать код. Код с сайта превращается в запись командой `npm run lock -- <код>`.
- **Генератор проверяет данные и останавливает сборку**: неверные штифты или связи, замок не решается, дубль, одинаковые штифты у двух подсказываемых замков, занятый адрес, нет обязательного текста. CI не задеплоит сломанный каталог.

**Не ломать.** Список замков правится только в `locks.yaml`. Решатель должен работать и без `locks-data.js` (`window.UML_LOCKS || []`).

## 4. Структура репозитория — PR #4

**Проблема.** В корне было 29 записей вперемешку: файлы сайта, воркер, тесты, документы. Деплой собирал сайт списком из шести `cp`, и новый файл легко было забыть.

**Решение.** `site/` — корень сайта, выкладывается целиком (`upload-pages-artifact path: site`). `worker/` — Cloudflare Worker и его скрипты. `tests/`, `tools/`, `docs/`. `locks.yaml` остался в корне как главный редактируемый файл. Тесты сами переходят в корень репозитория, `npm test` запускает все.

**Учесть.** Если к репозиторию подключён автодеплой воркера (Cloudflare Workers Builds), корневая папка там — `worker/`.

## 5. Плитки как в игре: 1 снизу — PR #5

**Проблема.** В игре плитка 1 нижняя (ближняя). 3D-схемы на сайте так и рисовали, а таблицы штифтов и связей, карточки каталога и страницы замков — наоборот.

**Решение.**
- Таблицы по умолчанию показывают 1 снизу; кнопка переворота осталась, выбор запоминается.
- Мини-схемы штифтов в каталоге и на страницах — тоже 1 снизу.
- Ссылки `?lock=` больше не переключают порядок. Раньше в коде был бит порядка строк, и таблица переворачивалась под того, кто отправил ссылку.
- **Бит порядка в коде всегда 0.** Иначе у одного замка два кода, и делятся счётчики «Открыт N раз» и копилка. Старые коды с битом 1 открываются как раньше. Пять кодов каталога с битом 1 приведены к каноничному виду (`ULWBAQhAKg` → `QLWBAQhAKg` и др.), их счётчики в копилке начались заново.

**Не ломать.** `encodeConfig` пишет бит порядка как 0, декодер его игнорирует (`tests/link-test.mjs`).

## 6. Деплой и домен — PR #3

Сайт копии: <https://gothic-remake-unlock-loot.pessom.xyz>. Домен задан в Settings → Pages и сохраняется между деплоями. Шаг `pages.yml`, который при каждом деплое прописывал домен через API, удалён: встроенный токен CI не может менять настройки Pages, и шаг всегда падал (раньше ошибку скрывал `|| true`). Опасно было и другое: в шаге был зашит `unlockmyloot.com`, и при успехе он затёр бы домен этого репозитория. Файл `site/CNAME` — справка.

## 7. Фронт работает без бэка

Бэк (`worker/`) нужен только общим данным: счётчику, копилке, аналитике, отзывам. Решатель, мастер, каталог и ссылки работают целиком в браузере. Все обращения к API идут в фоне с `.catch`, интерфейс ответа не ждёт; без API счётчик показывает резервное число.

**Не ломать.** Не делать решение или мастер зависимыми от ответа API.

## 8. Общий код RU и EN — PR #8

**Проблема.** `site/index.html` и `site/en/index.html` были двумя копиями по ~4,5 тысячи строк с одной логикой. Каждую правку делали дважды, и копии разошлись: в EN не отправлялась аналитика подстановки связей, по-разному были записаны одни и те же функции, у одной фразы было два перевода, одно CSS-правило отличалось.

**Варианты.**
- Один шаблон и сборка обеих страниц — дублирования нет совсем, но без сборки решатель не открыть, а зеркало из git перестало бы работать.
- Одна страница с подменой языка в браузере — поисковики увидели бы EN-страницу русской.
- **Выбрали:** общие CSS и JS, тексты интерфейса — в словарях; два HTML остаются (~450 строк разметки с текстами страницы, нужны поисковикам).

**Как устроено.**
- `site/assets/app.css`, `solver.js`, `app.js` — общие; основа — RU-код (EN отставал).
- Тексты по принципу gettext: русская фраза в `T('…')` — сама себе ключ, перевод — в `i18n.en.js`. Не нужно придумывать сотни ключей, код остаётся читаемым. Места с другим порядком слов — через подстановки (`T('… {n} …', { n })`), склонения — `plural()` с правилом из словаря (RU: 1 / 2–4 / 5+, EN: 1 / много).
- Перенос проверен сравнением старой и новой версии в браузере по 21 состоянию интерфейса (таблицы, решение, мастер на всех экранах, отзыв, подсказки, тур): RU совпал полностью, EN — кроме одной фразы, у которой было два перевода.

**Не ломать.** Новая русская фраза — только через `T()` и с переводом (`tests/i18n-test.mjs`). Не называть локальные переменные `T`. `?v=dev` в HTML заменяет CI.

## 9. Сайт не ходит в боевой API — PR #9

**Проблема.** Копия на `gothic-remake-unlock-loot.pessom.xyz` слала запросы на боевой `api.unlockmyloot.com`. Воркер не знал этот домен (CORS), ответы браузер не отдавал, но простые POST до сервера доходили: рос боевой счётчик «вскрыто N замков», после «Да» пополнялась боевая копилка. Ручные workflow (`purge-locks.yml`, `worker.yml`) тоже работали с боевым API — случайный запуск очистил бы чужую копилку.

**Решение.** Адрес API — в одном месте, `site/assets/config.js` (его читают решатель и каталог). Сейчас там домен самого сайта: своего воркера нет, запросы получают 404 от GitHub Pages и тихо игнорируются — сайт работает, но ничего не отправляет наружу. Сторона воркера переведена туда же: `ALLOWED`, workflow, скрипты в `worker/scripts/`.

**Не ломать.** В `worker/wrangler.toml` маршрут убран: воркер с `custom_domain` на домене сайта забрал бы домен у GitHub Pages. Для своего воркера нужен отдельный поддомен (например `api.gothic-remake-unlock-loot.pessom.xyz`) — его же поставить в `config.js` и `ALLOWED`. `id` KV в `wrangler.toml` — от боевого хранилища, для своего воркера его нужно заменить.
